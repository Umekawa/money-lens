# 大量データ時の追加調査（2026-09-23）

## 2026-09-26 の改善後の参考測定

検索文字列・日付順の再利用、5,000件超の明細で入力後120msの検索待機、CSV全文保持の解消を行った。旧記録は改修前の結果として残す。合成データを同じWindows/Chromium環境で各1回測定（`npm run perf:audit -- --tag=post-search-complete transactions-100k duplicate-files-30`）。結果はローカルの `artifacts/scale-audit/results-post-search-complete.json` に保存。

| 条件 | 取込 | 検索（表示まで・120msの待機を含む） | 5文字連続入力（最後の結果まで） | 保持JS heap | ファイル指紋の文字数 |
| --- | ---: | ---: | ---: | ---: | ---: |
| 10万明細・1ファイル | 417ms | 一致146ms・不一致141ms | 150ms | 22.9MiB | 45 |
| 1万明細・同内容30ファイル | 5037ms | 一致234ms・不一致142ms | 162ms | 15.1MiB | 1340 |

検索時間は入力イベントだけでなく、待機後の描画までを含めた値。旧測定とは監査コード・ブラウザ状態が異なるため厳密な同条件比較ではない。短い指紋は読み込み済みファイルの表示件数にのみ使い、明細の重複判定には使用しない。取込の再描画と単一ファイルの同期解析は残るため、#269の対応規模はまだ保証しない。

## 調査方法

- 個人CSV・`csvs/` を使用せず、合成CSVをブラウザのメモリ上に生成する。
- `scripts/audit-scale.mjs` はPlaywright Chromium上で本体の `load` と操作イベントを実行する。HTML/JS/CSSのみを仮想HTTPSオリジンに返すため、リポジトリ配信サーバーは起動しない。
- データ生成時間を除外して取込時間を測定する。16msタイマーの最大実行間隔とLong Tasks APIでメインスレッドの停止を測る。
- 検索・連続入力・ページ送り・月選択はイベント処理とレイアウト更新までの時間を測る。実入力から画面提示までのINPそのものではない。
- CDPの強制GC後にJS heapの保持量を測る。ブラウザ全体のメモリ使用量や取込途中のピーク使用量ではない。
- 金額・内容・日付は人工的な値。明細を60か月に分散し、通常条件では内容を一意にして重複除外による件数減少を防ぐ。
- 1万・10万・30万明細、同じ総行数を1/30/300ファイルへ分割、別名同内容30ファイル、多数不正行、15万資産行、中止、60か月の履歴を確認する。
- CPU 4倍スロットリングは低速CPUの影響を見る比較用であり、実スマートフォンのメモリ・I/O・描画性能を再現するものではない。

## 再実行

```powershell
npm ci
npx playwright install chromium
npm run perf:audit
```

特定条件だけの実行例:

```powershell
npm run perf:audit -- transactions-100k files-300 invalid-150k-mixed
```

ばらつきを確認する反復測定:

```powershell
npm run perf:audit -- --repeat=3 --tag=repeat transactions-100k files-1 files-30 files-300
```

`--repeat` は1〜5回、`--tag` は出力名の接尾辞を指定する。上記は `results-repeat.json` に保存される。

測定結果はgitignore対象の `artifacts/scale-audit/results.json` に保存される。OS・CPU・ブラウザ版・本体ソースのSHA-256を併記する。数値は環境や実行負荷で変わるため、固定の合否判定にはせず、同条件での改善比較に使う。

## 評価の観点

1. **正確性:** 除外件数が多くても正常明細を部分反映・二重計上しない。失敗時のデータ状態と取込結果が一致する。
2. **規模への追従:** 同じ総行数をファイル分割しただけで全件再処理が繰り返されない。
3. **操作応答:** 表示300行に限定しても、検索やページ移動が全データ量に強く依存していないか。
4. **中止:** 単一大容量ファイルの解析中にも操作を処理でき、押した時点と中止成立の差を説明できるか。
5. **メモリ:** データが増えない重複取込や失敗だけで、保持メモリ・ログDOMが増え続けないか。
6. **閲覧:** 数百ページや24か月を超える履歴にも、必要な位置へ直接到達できるか。

## 計測結果

### 環境・確度

- Windows 10.0.26200 / Intel Core i7-13700KF / RAM 64GiB / Node 22.19.0 / Chromium 153.0.8010.12。
- 本体 `app.js` SHA-256: `0414e3fb99e3b0c517bc2e25a6fb2326fcbaabbf6ded4a239eb2cf190ef58552`。
- 15種類の条件を調査し、主要10条件は各3回実行。以下は注記がない限り3回の中央値。小数を含む時間の精度は測定環境のもの。
- 初回結果: `artifacts/scale-audit/results.json`、反復結果: `results-repeat.json`、集約: `summary.json`（いずれも同ディレクトリ）。
- 正常系の反復では件数と支出合計を別計算の期待値と照合済み。不正行による二重計上は3回すべてで再現。

### 行数による違い

| 明細数 | 取込 | 取込中の最大タイマー間隔 | 一致検索1回 | 5文字連続入力の合計 | 次ページ | 操作後の保持JS heap |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 1万（初回1回） | 40ms | 51ms | 24ms | 95ms | 24ms | 3.0MiB |
| 10万 | 328ms | 341ms | 190ms | 855ms | 181ms | 17.8MiB |
| 30万 | 974ms | 977ms | 550ms | 6252ms | 1358ms | 51.3MiB |

30万件の5文字連続入力は6149〜7310ms、次ページは1311〜1526msだった。合成イベントを休止なしで発火した処理時間であり、通常の打鍵間隔やINPの値ではない。各入力・ページ移動で全件の検索文字列正規化、フィルター、ソートを行うため、DOMが300行でも処理量が減らない。検索結果・ソート済み順序の再利用と、入力ごとの不要処理の削減が必要。

10万件をCPU 4倍スロットリングで実行した比較ケース（1回）は取込1405ms、一致検索811ms。実端末での低速環境確認も必要。

### 同じ3万明細をファイル分割した場合

| ファイル数 | 取込中央値（範囲） | 全画面render回数 | render累計中央値 |
| --- | ---: | ---: | ---: |
| 1 | 113ms（112〜115） | 1 | 62ms |
| 30 | 1329ms（1322〜1341） | 30 | 947ms |
| 300 | 27151ms（24001〜27835） | 300 | 20470ms |

総行数は同じでも300分割すると約240倍。300ファイル条件では約75%をrender内で消費した。ファイルごとに全件キーの再構築・全画面集計・検索/ソートを繰り返す構造が支配的。進捗表示は軽量に更新し、マージ用索引の再利用・描画頻度の制御・バッチ処理を優先したい。いずれも明細3万件、支出15015000円の正確性は維持されていた。

### 重複CSVとメモリ

300文字の付加テキストを持つ同じ1万明細を、別名にした同内容CSVで取り込んだ。

| 条件 | 最終明細数 | 取込中央値 | 保持JS heap | loadedFiles内の文字数 |
| --- | ---: | ---: | ---: | ---: |
| 1ファイル | 10000 | 127ms | 14.6MiB | 3329519 |
| 同内容30ファイル | 10000 | 5878ms | 198.9MiB | 99885590 |

データ件数・金額は増えないのに保持heapが約184MiB増加。ファイル名＋全文を重複キーにしているため、別名の同内容ファイルごとに全文を保持する。内容ハッシュ等の短い識別子への変更が必要。失敗ファイルの全文保持も対象に含める。

クリア後のJS heapは約1.4〜1.5MiBに戻った。一方、表や結果詳細のDOMは残留するため、JS heapだけを見て表示データも破棄されたとは判断できない。

### 中止・大量エラー・長期履歴

- **中止:** 30万件で取込開始50ms後に中止ボタンのclickを予約したが、実際の実行は983〜1009ms後、中央値997ms。全3回でその時点には取込完了・30万件反映済みだった。初回ボタン非表示問題とは別に、同期解析/描画中にはイベントを処理できない。分割処理・Worker等でタスクを譲る必要がある。
- **5万件のエラー:** 取込128ms、詳細展開400ms。閉じたdetailsにも50006要素を作る。展開後の文書はテキスト等を含め100282ノード、クリア後も100281ノード。仮想化/ページングや件数集約が必要。
- **15万件の不正行＋正常2行:** 取込は失敗扱いだが正常行が部分反映され、既存seed明細を二重計上。支出300円の期待に対し400円を全3回で確認。性能改善より先に例外時の反映規則を直す必要がある。
- **15万資産行（初回1回）:** 同日の合成資産を15万行取り込むと引数展開の上限超過で0件、既存#151の不具合をChromiumでも確認。
- **60か月（初回1回）:** 60件の資産を保持しても最新24か月しか閲覧できず、古い月を選択しても資産内訳へ到達できない。計算量と別に表示範囲の移動手段が必要。
- **10万明細のモバイル:** 334ページになる。390px幅の第2ページで、ページ操作は文書上端から21324pxに配置。前後移動だけでは目的のページへの到達が困難。

### 対応の順序

1. #168: エラー時の部分反映・二重計上を解消し、データの正確性を保証する。
2. #151: ファイルごとの全画面再計算、検索/ソートの繰返し、全文重複キー、中止不能を段階的に改善する。
3. #169・#158: エラー詳細のDOM上限とクリア後の解放を実装する。
4. #170・#171: 古い履歴と大量ページへの移動を改善する。

改善後の目安として、同じ環境の10万件で検索/ページ操作100ms以内、処理中の入力待ち100ms以内、3万件を300分割した取込3秒以内を候補にする。これは今回達成した保証値ではなく、実利用量と低速端末の確認を経て採用する性能予算案。最優先の不変条件は件数・金額の正確性と、失敗/中止時の整合性である。

### A [P1] 大量の不正行で取込が例外終了すると正常明細が部分反映され二重計上される

**再現:** 既存明細 `2026-01-01,seed,食費,-100,1` を取り込む。続いて同じ明細1行、新規 `2026-01-02,new,食費,-200,1`、不正日付 `2026-99-99` の15万行を含むCSVを取り込む。`npm run perf:audit -- invalid-150k-mixed` で再現可能。

**実結果:** 「失敗・成功0件・除外0件・Maximum call stack size exceeded」となるが、stateにはseedが2件とnewが1件の計3件残る。支出は本来300円のところ400円となる。最初のChromium測定ではmergeTransactions呼出0回、seedCopies=2を確認。

**原因:** `parseFile` が正常行を直接stateへ追加してから `state.importMessages.push(...invalid)` で引数上限を超える。`load` のcatchへ移るため、その後の重複マージ・件数集計が実行されない。失敗したファイルの全文キーも取込済みとして残る。

**完了条件:** 大量メッセージを引数展開せずに扱う。解析・検証とstate反映を分け、例外時に全体ロールバックまたは明示した部分成功の規則を保証する。途中例外でも重複排除を飛ばさず、取込結果とデータ件数・金額が一致すること。15万不正行＋正常/重複行、正常行なし、再取込、後続正常ファイルを合成データで検証する。

**関連:** #151は資産行の配列展開と性能の課題。本件は明細のエラー記録時例外によるデータ不整合として独立させる。#148の結果表示にも関連。

### B [P2] 大量の取込エラーを折りたたみ内でも全件DOM化し上限なく蓄積する

**再現:** `npm run perf:audit -- invalid-50k`。5万行を不正日付として取り込む。

**実結果:** 取込結果は閉じたdetailsでも50006要素、文書全体は50123要素となる。クリア後も取込結果の50006要素がDOMに残る。`renderDashboard` と後付け `render` の双方で全メッセージをHTML化するため同じ取込で2回生成する。

**影響:** 正常明細は300行に表示制限されているが、エラー表示に同様の制限がない。失敗や再試行が増えると文字列保持・DOM生成・詳細表示・支援技術への通知が肥大化する。

**完了条件:** エラー総件数と表示サンプルを分け、詳細をページング/遅延描画する等でDOM量を制限する。必要な行番号・理由の追跡可能性を保つ。全メッセージの二重描画を除き、5万件以上でも展開・閉じる・クリアの応答を計測する。クリア後は詳細DOMも解放する。

**関連:** #158の消去問題に加え、エラー表示自体のスケーラビリティ。Aの例外安全性とは独立して改善する。

### C [P2] 24か月を超える履歴の資産内訳と月次比較へ到達する手段がない

**再現:** `npm run perf:audit -- history-60-months`。2021年1月〜2025年12月の60か月分の明細・資産を取り込む。

**実結果:** 資産は60件保持されるが、表示は2024年1月以降の24件のみ。月次グラフも同期間のみ。月フィルターで2021年1月を選んでも両グラフの期間は変わらず、2021年1月の資産内訳へ到達できない。表示上限はREADMEに記載済みであり、仕様上の制限を改善する機能課題。

**完了条件:** 過去期間を選択・移動できるグラフまたは履歴表を提供する。描画上限を維持しながら、全期間の資産記録・内訳と月次集計に到達できること。60か月、欠損月、日次/月次混在で古い期間と最新期間の切替を検証する。

**関連:** closed #14、#64。既存#151の速度問題とは別に、長期間データの閲覧機能の課題。

### D [P2] 大量明細の数百ページを前後ボタンだけで移動し、モバイルでは操作位置も遠い

**再現:** `npm run perf:audit -- transactions-100k`。10万明細は300件ずつ334ページになる。390px幅では300行の表が通常フローで伸び、測定時のページ操作位置は文書上端から21324pxだった（この測定は第2ページ表示）。

**根拠:** `renderTransactions` は前の300件・次の300件だけを提供し、ページ直接指定・先頭/末尾移動・ページサイズ選択はない。`styles.css` のモバイル規則は `.table-wrap{max-height:none}`。ページ送り後のフォーカスは表の後ろのページ番号へ移るため、新しいページの先頭を読むには大きく戻る必要がある。

**完了条件:** 先頭/末尾・ページ指定や期間指定等、対象位置へ少ない操作で到達する手段を用意する。モバイルで適切な表示件数と操作位置を選び、切替後は新しい明細の開始位置を把握できること。10万件以上、キーボード、390px幅、検索/月変更後で検証する。

**関連:** closed #4、#44。300件以降を表示できること自体は実装済みだが、大量ページの移動とモバイル操作を改善する。
