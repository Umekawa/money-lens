### 01 [P1] デモと追加CSVが混在し、実データ表示でもデモ表示が残る

**確認:** ブラウザ再現。`app.js` の `loadDemoData`・`load` と `styles.css` の `.demo-badge`。

デモ起動後に合成の収入100円を追加すると、デモ7件と混在して8件・収入560,100円になる。`state.demo` はtrueのままで「匿名のサンプル」と表示される。逆順の操作でも混在する。また `hidden=true` のバッジも `display:inline-block` により表示される。

**対応・完了条件:** デモとユーザーデータの切り替え規則を定義し、混在による誤集計を防ぐ。起動→取込、取込→デモ、クリア後の各経路で実際のデータと案内が一致し、hidden指定が確実に非表示になることを検証する。

**関連:** #17、#27。

### 02 [P1] 資産CSVの種別判定と合計列選択がファイル名・列順に依存する

### 03 [P1] 日付を検証・正規化せず取り込み、月次集計と最新資産日が不正になる

**確認:** ブラウザ再現。`parseFile`・`renderMonthlyTrend`・`renderAssets`。

`2026/1/5` と `2026-99-99` が警告なしで取り込まれ、月候補に `2026/1/` と `2026-99` が出る。前者は月別推移から脱落し、後者は架空の月として集計される。期間・資産の最新日は文字列比較に依存する。月候補は `innerHTML` への挿入時にエスケープされていない。

**対応・完了条件:** 対応日付形式を定義し、実在日を検証して統一形式に正規化する。閏日・スラッシュ形式・ゼロ埋め・不正文字列を検証し、全表示で同一の期間になること。無効行に行番号と理由を表示し、HTML出力もエスケープする。

### 04 [P1] 空の金額や不正な資産内訳が0円として取り込まれる

**確認:** 空金額はブラウザ再現、その他はコード確認。`parseFile`。

金額が空の明細が警告なしで0円として取り込まれる。`Number('')` は0となり、不正な資産内訳も `Number(...) || 0` で0になる。内訳のInfinityや円表記などに対する検証・対応方針もない。

**対応・完了条件:** 空欄、0、欠損列、不正値を区別し、総額・明細・内訳すべてに一貫した数値検証を適用する。対応する桁区切り・通貨表記を明記し、非有限値・安全に扱えない値で集計が破綻しないことを検証する。

**関連:** #11。

### 05 [P2] 壊れたCSV構文や文字コードを検出せず処理する

**確認:** コード確認。`parseCSV`・`decode`。

閉じていない引用符、引用符位置、ヘッダーと行の列数不一致を検証しない。UTF-8として読めないデータを無条件にShift_JISとして復号し、置換文字が発生しても利用者に伝えない。

**対応・完了条件:** 正常な引用符内改行・二重引用符を維持しつつ構文エラーを検出する。UTF-8/BOM/Shift_JISの実バイト列と不正バイトをテストし、未対応形式・破損データをファイル名と原因付きで案内する。

**関連:** #3、#11。

### 06 [P1] 1ファイルの読み込み例外で後続ファイルも停止し、画面に失敗が出ない

**確認:** ブラウザ再現。`load`・`parseFile` とchangeイベント。

先頭ファイルの `arrayBuffer()` を失敗させ、次に正常なCSVを渡すと、Promiseがrejectされ後続は0件、画面の警告も0件になる。イベント側にもcatchがない。途中まで成功したデータの再描画も保証されない。

**対応・完了条件:** ファイル単位で例外を捕捉し、後続ファイルを処理する。成功・失敗・一部成功を画面に出し、未処理のPromise rejectionを発生させない。先頭・途中・全件失敗を検証する。

**関連:** #11の未充足条件。

href文字列の連結と再帰に依存し、URLのエンコード・配信範囲・循環を管理しない。各CSVレスポンスのresponse.okを確認せず、途中失敗はconsole.infoのみ。先に取り込まれたデータもrender前に例外になると画面に反映されない。GitHub Pages判定はgithub.ioホストだけで、カスタムドメインでは探索が走る。

**対応・完了条件:** 自動読込を実行する環境を明示設定し、URLを正規化して対象範囲と訪問済みを管理する。HTTPエラー・異常な一覧・途中失敗を適切に案内し、一部成功の扱いを定義する。すべてモック応答で検証する。

### 23 [P1] 自動開発がIssue本文・優先度を渡さず、既存変更も無関係なIssueに紐付ける

**確認:** コード確認。`scripts/autodev.ps1` のIssue選択、`issueInstruction`、`PublishCurrentChanges`。

最新20件から番号順で選び、本文・受入条件・依存関係を取得せず番号と題名だけを指示する。20件より古い未解決課題が対象から漏れる。`-PublishCurrentChanges` でも同じ自動選択を行い、既存差分との関連確認なしにClosesを付けるため無関係なIssueを閉じ得る。

**対応・完了条件:** 明示Issue番号指定と本文取得を設け、優先度・依存関係を考慮した選択方針を決める。既存変更の公開では対象Issueを明示するかClosesを付けない。20件超・Issue取得失敗・既存変更のモックケースを検証する。

### 24 [P1] 自動レビューの合格判定とマージがレビュー対象コミットに固定されていない

**確認:** コード確認。`scripts/autodev.ps1` のレビュー判定、`Publish-LocalChanges`、checks、merge。

レビュー中に作られたコミットは、作業ツリーがcleanならそのままpushして合格にできる。一方、未コミット修正では再レビューを要求しており扱いが不一致。statusCheckRollupは何か1件あれば待機を進め、指定の必須チェック成功・レビューしたHEADとの一致をスクリプトで確認していない。マージも期待HEADを固定しない。

**対応・完了条件:** レビュー開始/終了とpush後のSHAを管理し、レビュー中に変化したコードは再レビューする。必須チェックの名前と成功状態を同じSHAで確認し、期待するHEADに限定してマージする。修正コミット、skipped/未登録チェック、HEAD変更をモックで検証する。

### 25 [P2] GitHub Pagesがリポジトリ全体をチェックなしで公開する

**確認:** コード確認。`.github/workflows/pages.yml`。

公開アーティファクトのpathが `.` で、配信に不要なscriptsやドキュメント等も対象になる。Pagesワークフローにnpm run checkの依存がなく、mainへの直接pushや手動実行では公開前の検証が保証されない。

**対応・完了条件:** HTML・JS・CSS等の公開に必要なファイルだけを専用ディレクトリへ収集する。公開前にチェックが成功する依存関係を設け、配信一覧を確認できるようにする。公開対象に個人ファイルを混ぜず合成ファイルで検証する。
