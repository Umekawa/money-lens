## リリース前に残る問題

### 1. Pagesデプロイ失敗（公開の阻害要因）

- [最新のDeploy GitHub Pages](https://github.com/Umekawa/money-lens/actions/runs/35999035644) は対象SHAと一致し、`actions/configure-pages@v5` で失敗。
- ログ: `Get Pages site failed` / `Not Found`。Pages APIの読み取りもHTTP 404。
- 設定未完了・利用条件・権限の切り分けが必要。まずSettings → PagesでGitHub Actionsによる公開が有効か確認する。404だけで原因を一つに断定しない。
- 成功した公開デプロイとリリース対象SHAを照合できるまで、公開版のリリース判定は保留。

### 2. #151は資産取込の例外だけ解消し、性能の完了条件が残る

今回の測定は各条件1回の探索的測定で、環境負荷によるばらつきを含む。過去の `docs/scale-audit-2026-09-23.md` と同種の問題を再確認した。

| 条件 | 今回の実測 |
| --- | --- |
| 10万明細 | 一致検索230ms、次ページ232ms |
| 30万明細 | 取込1.13秒、5文字連続入力9.91秒、次ページ1.87秒 |
| 同じ3万明細を1ファイル/300ファイル | 152ms / 39.75秒。300ファイルではrender累計31.47秒 |
| 同内容1万明細を別名30ファイルで取込 | 明細は1万件のまま、保持JS heap約199MiB、全文キー約9990万文字 |
| 単一30万行の取込を50ms後に中止予約 | イベント実行は約1173ms後。その時点で取込終了、30万件が反映済み |

5文字連続入力は休止なしの合成イベント処理であり、通常の打鍵やINPの値ではない。heapは操作後・強制GC後の保持量で、ピークメモリではない。

根拠: `app.js` の `renderTransactions` は操作ごとに全件の検索文字列生成・フィルター・ソートを実行し、`parseFile` はファイル名と全文をキーとして保持する。対応PR #185の変更は資産行の追加方法とそのテストで、これらの改善は含まれていない。

完了には、合意したデータ規模と応答時間の基準、描画頻度の制御、検索/ソート結果の再利用、全文保持の削減、単一ファイル処理中のイベント応答の改善が必要。複数ファイルの間で中止できることと、単一ファイル解析中に中止できることは別条件。

- 再現: 匿名デモを幅320pxで表示する。

- 横にはみ出さないため既存の横幅監査は成功するが、金額の読み取りを損なう。狭幅で1列化するなど、金額を一続きで読める表示と検証が必要。
